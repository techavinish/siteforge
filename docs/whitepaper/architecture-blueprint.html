SiteForge — an AI Copilot that builds business websites

A learning-driven build: one real product, every layer of the modern agent stack. You ship a copilot that interviews a business owner, generates their website, deploys it, and continuously evaluates its own output.

GCP + Firebase Terraform LangGraph Temporal OpenRouter Remote MCP Postgres · ClickHouse · Redis Sentry
01

What you're building

The product: a chat copilot for small-and-medium businesses. The owner signs in with Google, describes their business ("I run a bakery in Jaipur, I want online orders"), and the agent plans the site, writes the copy, picks a template and theme, assembles the pages, and deploys a live website to Firebase Hosting. Afterwards the owner iterates conversationally — "make the hero warmer", "add a pricing page" — and every published site is re-evaluated on a schedule for quality, SEO, and accessibility.

The real goal: the product is the excuse; the stack is the curriculum. Every piece below exists to teach you one concept properly, and each phase of the plan ends with something deployed and demoable.

User journey (happy path)

  1. Sign in — Google SSO via Firebase Auth.
  2. Interview — the LangGraph agent asks structured questions about the business.
  3. Generate — a Temporal workflow durably runs: plan → retrieve (RAG) → write copy → assemble pages → build.
  4. Deploy — the site goes live on a Firebase Hosting subdomain (bakery-jaipur.web.app).
  5. Iterate — chat edits trigger targeted regeneration, versioned in Postgres.
  6. Evaluate — a nightly cron scores every live site with an LLM judge; scores land in ClickHouse and feed back into the agent's examples.

03

Temporal vs LangGraph — get this mental model right first

Correction to your notes

Your notes have it inverted: Temporal is the deterministic side, and the LLM/agent is the non-deterministic side. A Temporal workflow must be strictly deterministic (that's how it can replay and survive crashes). Anything non-deterministic — every LLM call, every external API — is wrapped in a Temporal activity, which is allowed to be flaky and gets automatic retries.

So the two are not competitors — they nest:

  • LangGraph is the agent's brain: a graph of nodes (interview → plan → retrieve → write → critique → assemble) with tools/actions and integrations. It decides what to do next within a reasoning session.
  • Temporal is the spine: it makes the multi-minute site-generation job durable. If a worker dies mid-generation, the workflow resumes exactly where it left off. It owns retries, timeouts, human-in-the-loop signals ("owner approved the draft"), and the deploy step.
  • The pattern: a Temporal workflow orchestrates the job; one of its activities runs the LangGraph agent; the agent calls OpenRouter and tools inside that activity.

04

Data platform — medallion layers on ClickHouse

Three stores, each with one clear job. Postgres (Cloud SQL) is the operational database: users, projects, sites, page versions, LangGraph checkpoints, and pgvector embeddings for RAG. Redis (Memorystore) handles caching, rate-limit counters, and pub/sub for streaming tokens to the UI. ClickHouse is the analytical store where the medallion architecture lives:

Bronze

Raw, append-only. Every LLM request/response, agent trace, chat transcript, Temporal event, tool call — landed as-is with a timestamp. Never edited, only appended.

Silver

Cleaned & typed. Parsed traces: one row per agent step with model, latency, token counts, cost. Eval results normalized to a fixed rubric schema. Built with scheduled ClickHouse materialized views.

Gold

Business aggregates. Cost per generated site, generation success rate, eval-score trends per template, p95 generation latency — the tables a dashboard reads directly.

Platinum

Agent-facing feedback loop. The highest-scoring sites and copy become curated few-shot examples, exported back into the RAG corpus. This layer is what makes the system self-improving — and it's the most interesting part of your whitepaper.

05

Evaluation layer

Cloud Scheduler fires a cron (nightly to start). The eval-service pulls every site published or updated since the last run and scores it with an LLM judge through OpenRouter against a fixed rubric:

  • Content quality — is the copy specific to this business, or generic filler?
  • SEO basics — titles, meta descriptions, heading structure, alt text.
  • Accessibility — contrast, landmarks, form labels (mix of LLM judge + deterministic checks like Lighthouse).
  • Brand consistency — does the tone match what the owner asked for in the interview?

Scores are written to ClickHouse (bronze → silver), trends surface in gold, and top performers graduate to platinum. Key learning here: always pair the LLM judge with deterministic checks — the judge for taste, scripts for facts.

08

Keeping cost near zero

  • Cloud Run scales to zero — dev environment costs pennies. Keep only the Temporal worker warm when actively testing workflows.
  • Temporal: dev server locally (free); Temporal Cloud's free credits when you need hosted, or a small self-hosted instance.
  • ClickHouse: run it in docker-compose until phase 8; single small VM or Cloud trial after.
  • OpenRouter: use cheap/free-tier models for development loops, switch to a strong model only for final generation and judging. Your bronze layer gives you exact per-call costs from day one.
  • Cloud SQL is the one fixed cost — smallest tier (db-f1-micro) for dev, and stop the instance when idle.
09

Design review (v2) — gaps found & fixes

A deep pass over v1 surfaced one architectural trap and five smaller gaps. All fixes are folded into the phase plan; this section records what changed and why.

1 · Firebase Hosting caps at 36 sites per project ⚠️

The plan deploys each customer site as a Firebase Hosting sub-site — but Firebase allows a maximum of 36 sites per project. Fine for the learning build; a real product would hit the wall at customer #37. The fix costs nothing now: put deploys behind a SiteDeployer interface from day one, with Firebase as the first implementation. The production-scale swap later is a GCS bucket + Cloud CDN (one bucket path per site, effectively unlimited) — a one-class change instead of a rewrite. Designing behind an interface because a quota exists is itself a lesson worth having.

2 · No cost guardrails — anyone with a Google account can spend your money

Google SSO is open sign-up, and every generation burns OpenRouter tokens. Three cheap defenses, all added to the plan: a per-user generation quota in Redis (e.g. 3 sites/day) enforced at the gateway (P4); GCP budget alerts declared in Terraform — billing guardrails as code (P1); and a hard spend limit on the OpenRouter key (P4).

3 · No content-safety gate before publishing

Generated sites publish under your Firebase project — if a user asks for a phishing page or scam storefront, you're the publisher. Fix: a moderation activity in the Temporal workflow between "assemble" and "deploy" — a cheap model call that classifies the site against a blocklist (fraud, impersonation, adult, illegal) and fails the workflow with a clear reason. Slots naturally into P5 and doubles as a lesson in guarding agent outputs, not just inputs.

4 · Temporal workers don't fit Cloud Run's default model

Cloud Run bills per request and idles CPU between requests — but a Temporal worker isn't a web server; it long-polls the task queue continuously. It needs min_instances = 1 with instance-based billing (CPU always allocated) — roughly $10–15/month, the one always-on cost in the system (trial credits absorb it; run the worker locally against the Temporal dev server outside credit windows). Knowing why pollers break request-based autoscaling is a genuinely useful piece of platform knowledge.

5 · No testing story for the agent

The eval cron scores production output, but nothing stops a prompt change from shipping a regression. Fix: a golden set of ~10 synthetic businesses (bakery, law firm, gym…) built in P4, run through the graph on every PR that touches prompts or graph code, scored by the same judge rubric — merge blocks if scores drop (automated in P8). Plus Temporal's replay testing in P5 to prove workflow changes don't break in-flight generations. Offline evals in CI is arguably the highest-value habit in the whole project.

6 · Generated sites have no images

v1 generated copy and layout but no visual assets — every site would ship as text soup. Fix: a pick_images tool on the agent (P6) that searches a free stock-photo API (Pexels/Unsplash) by scene description, plus a GCS bucket for per-site assets in the Terraform baseline. Image selection quality also becomes a rubric line in the eval layer.

Minor items (one-liners, folded into phases)

  • Public-repo secret hygiene — enable GitHub push protection + a gitleaks CI job in P0, before any cloud credential exists.
  • Cloud SQL backups — automated backups + point-in-time recovery flags in the Terraform module (P3), not clicked on later.
  • ClickHouse ingestion — use async inserts / small batches from services rather than row-at-a-time writes (P8).
  • Redis connection pools — keep pools small (2–3 per service); serverless instances multiply connections fast (P9).
